# FastPaperRead 待办任务与时间计划（2025-12-22）

> 目标：让后续执行人员**按这个文件即可推进开发**。  
> 取舍结论：**API 以当前代码实现为准（source of truth）**，`docs/API接口设计.md` 视为“曾经的目标设计/已过时草案”，需要更新为“当前实现 + 计划演进”两部分，否则会持续误导前后端对接。

---

## 1. 总体原则（执行时必须遵守）

- **优先级 P0**：保证前后端能端到端跑通主流程（导入→Overview→Read→卡片/清单→导出）。
- **对齐策略**：短期采用“**兼容**”而不是“推翻重写”
  - 后端尽量同时兼容两套参数/路径（例如 `page/limit` 与 `skip/limit`），避免前端/脚本大量修改。
  - 文档同步更新，明确“已实现/未实现/计划”。
- **可交付定义**：每个任务必须有“验收标准（如何验证）”。

---

## 2. P0（本周必须完成：让系统真正可用）— 预计 2~3 天

### P0-1：前后端 API 对齐（最关键）— 预计 0.5~1 天

- **问题**：当前 `frontend/src/lib/api.ts` 与后端 `backend/app/api/v1/*` 在路径、参数、返回结构上不一致，导致页面调用报错或数据错位。
- **执行**（推荐：后端做兼容层 + 文档同步）
  - **Papers 列表**：兼容 `page/limit` 与 `skip/limit`；统一返回 `{ items, total, page, limit }`（或在后端同时返回 `papers/items` 双字段，逐步迁移）
  - **Papers 统计**：兼容 `/papers/stats/overview` 与 `/papers/stats`
  - **Export**：实现 `POST /export` 作为“统一导出入口”，内部复用现有 `/export/{paper_id}/markdown|json|bibtex`
  - **Export Notes**：实现 `GET /export/paper/{paper_id}/notes`（至少 markdown），内部可复用卡片+清单+skim 的 markdown 拼装
- **验收**
  - 文献库、Overview 页面、导入进度轮询不报 404/422
  - 导出按钮（至少能导出 markdown/bibtex）可用

### P0-2：Skim 队列/关键图接口补齐（按现有前端调用）— 预计 0.5~1 天

- **补齐后端路由**
  - `GET /api/v1/skim/queue`：返回待读队列（可先用 DB 表或简单字段；不建议内存）
  - `DELETE /api/v1/skim/queue/{paper_id}`：从队列移除
  - `GET /api/v1/skim/{paper_id}/key-figures`：返回关键 figure anchors（可先按 `type=figure` 取前 N 个 + 简单排序）
- **前端**
  - Library/Overview 的“加入队列/跳转队列页”需要补一个 `/queue` 页面或改为返回 Library（两者择一）
- **验收**
  - Overview 点击“加入队列”不会跳到不存在页面
  - 能看到队列列表并移除

### P0-3：Read 精读页与后端卡片/清单真正落库 — 预计 1 天

- **当前问题**：`paper/[id]/read/page.tsx` 里卡片/清单大量只存在本地 state/localStorage。
- **执行**
  - 卡片：创建/更新/删除改为调用 `cardApi.create/update/delete`；创建后刷新列表
  - 清单：右侧 `ChecklistPanel` 改为调用 `checklistApi.generate/get/updateItem/setVerdict`
  - “扫描缺失项”按钮：直接调用 `enhance` 或 `checklist.generate`（先接通即可）
- **验收**
  - 刷新页面后卡片/清单仍存在（来自后端）
  - 清单可生成、可勾选 found、可跳转到 anchor

## 3. P1（下周：把高级页面从 Mock 变成真实功能）— 预计 3~5 天

### P1-1：Notes 笔记库接后端 — 预计 1 天

- **执行**
  - `notes/page.tsx` 用 `cardApi.search` + 支持类型筛选、关键词搜索
  - 卡片点击进入详情（可先弹窗/抽屉）
- **验收**
  - Notes 展示真实卡片；搜索可用

### P1-2：Compare 页面接后端 compare API + 持久化 — 预计 1~2 天

- **当前问题**：后端 compare 使用内存 `_compare_sets`（重启丢失）；前端 Compare 纯 mock。
- **执行**
  - 先让前端调用 `compareApi.createSet/generateMatrix`
  - 再把 compare set 存到数据库（新增表 `compare_sets`）
- **验收**
  - 任意两篇真实论文能生成对比矩阵
  - 重启后 compare set 仍可打开

### P1-3：Review 页面接后端 review API + 持久化 — 预计 1~2 天

- **执行**
  - 前端生成草稿：调用 `reviewApi.generateDraft`
  - 保存反馈：调用 `reviewApi.submitFeedback`
  - 导出：调用 `reviewApi.exportReview`
  - 后端 review 当前用内存 `_review_drafts`：迁移到 DB（新增表 `reviews` / `review_feedback`）
- **验收**
  - 真实论文可生成审稿草稿、保存评分与问题列表、导出 markdown

## 4. P2（增强体验与架构一致性）— 预计 4~7 天

### P2-2：Anchor ↔ Card 关联 — 预计 1 天

- **验收**

### P2-3：DOI/arXiv 元数据补全 — 预计 1~2 天

- **验收**

## 7. 风险与依赖（执行前先确认）

- **数据库**：当前 repo 中存在 `fastpaperread.db`（疑似 SQLite），文档里曾写 PostgreSQL；需要统一（建议短期继续 SQLite，后续再迁移）
- **LLM Key/模型**：增强与生成依赖外部模型；需要准备 `.env`/配置与失败降级策略
- **解析器**：PDF 解析质量不稳，需要明确降级策略（只做文本层/只抽 section/只抽 figure）
